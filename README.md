# Gloomhaven: Jaws of the Lion - Unofficial Companion App

![License](https://img.shields.io/badge/license-GPLv3-green.svg)
![React](https://img.shields.io/badge/react-19-blue)
![PWA](https://img.shields.io/badge/PWA-Ready-purple)

An offline-first companion app for the board game **Gloomhaven: Jaws of the Lion**. It keeps the campaign between sessions and answers rules questions without replacing the physical tabletop experience. The current version is shown in Settings, in the About section, and comes from `package.json`.

The app is unofficial. Every row of its game data names its source: a page of the Learn to Play Guide (`LtP p.N`) or of the Rules Glossary (`Glossary p.N`), a page of the Scenario Book (`SB p.N`), the printed card (`card`), or the community data of Gloomhaven Secretariat (`GHS`) where the books are silent. Rules texts are short paraphrases, not copies; at the table the books have the last word. The app does not replace the Scenario Book: maps, setup, special rules and story stay there.

## Features

- **Campaign management:** several campaigns, scenario unlocks and party progress.
- **Character sheets:** HP, XP, gold, perks and battle goal checkmarks; the hand for the next scenario is chosen from the cards of the campaign stage (A/B, level 1, X, cards gained at level-up) within the hand size; items owned and items brought into the next scenario are kept apart, the shop checks gold and the copies in the party.
- **Scenario tracker:** locked, unlocked, completed and closed scenarios (completing a branch closes its alternative); goal and location, with monsters, treasures and rewards behind a spoiler button.
- **Tools:**
  - learning scenarios 1 to 5: what each introduces and what changes after it, bound to the campaign,
  - set up scenario: briefing of the next scenario (spoilers behind a reveal) and the scenario level calculator,
  - finish scenario: records gold, experience, checkmarks, reward perks and items, completes the scenario with its unlocks and closes, logs the result and lists what is left at the table.
- **Rules reference:** glossary with page numbers, the round on one screen, conditions, elements, short guides and the monster turn step by step.
- **Offline first:** a Progressive Web App; campaigns are stored in the browser (IndexedDB).
- **Data portability:** export and import of campaign data as JSON backups. An old backup is converted on import like stored data (database version 2: items 37 to 52 refunded, card names to card ids; version 3: cards of level 2 and above split off as cards gained at level-up, an empty scenario log).

## Tech stack

- React 19, TypeScript 5.9 (strict), Vite 8
- Tailwind CSS v4
- Zustand 5 for state, Dexie.js (IndexedDB) for persistence, Zod v4 for validation of stored and imported data
- vitest for tests, ESLint for linting
- nginx in the production image

## Getting started

Prerequisites: Node.js 24 (see `.nvmrc`) and pnpm 10 (the exact version is pinned in `packageManager`). npm and yarn are not used.

```bash
git clone https://github.com/Sinimus/jotl-companion.git
cd jotl-companion
pnpm install
pnpm dev
```

| Command | What it does |
|---|---|
| `pnpm dev` | development server |
| `pnpm lint` | ESLint |
| `pnpm test` | vitest, one run |
| `pnpm build` | type check and production build into `dist/` |
| `pnpm preview` | serves the production build locally |

## Icons and install

The app icons are drawn for this project (`design/icons/*.svg`, a letter J on amber). The PNG files in `public/` (192, 512, maskable 512, and the 180 px `apple-touch-icon`) are rendered from them with `design/icons/render.sh`, which needs a Chromium on the path. The web manifest is generated by `vite-plugin-pwa` from `vite.config.ts`; there is no manifest file in `public/`.

## Docker

The production image is a two-stage build: Node 24 builds the app, `nginx:stable-alpine` serves it on port 80. The image has a `HEALTHCHECK` (busybox `wget` on `127.0.0.1`). `nginx.conf` sends `no-cache` for `index.html`, `sw.js`, `registerSW.js` and the manifest so that new versions reach installed apps, and caches the hashed files in `/assets/` for a year.

```bash
docker build -t jotl-companion .
docker run --rm -p 8080:80 jotl-companion
```

## Continuous integration and deployment

- **Pull requests to `main`** (`.github/workflows/pull-request.yml`): `pnpm lint`, `pnpm test`, `pnpm build`, then a Docker build without push and a smoke test of the container (HTTP 200, page title, cache and security headers, manifest type, a hashed bundle, the healthcheck command).
- **Push to `main` and manual runs** (`.github/workflows/docker-publish.yml`): builds the image, pushes it to GitHub Container Registry and triggers the redeploy of the hosting platform. The deploy call answers 200 even when the rollout fails afterwards, so a deployment is verified by the hash of `assets/index-*.js` in the served `index.html`, which must match the build of the merged `main`.
